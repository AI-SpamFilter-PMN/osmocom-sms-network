# AI-Powered SMS Spam Filter over Virtual GSM Network

This telecommunications applications development graduation project demonstrates **end-to-end mobile network routing and intelligent SMS payload inspection**.

The project implements a fully virtualized **2G GSM network** capable of intercepting, evaluating, filtering, and delivering SMS messages using a **Large Language Model (LLM)** integrated through a **Java Spring Boot SMPP middlebox**.

The architecture supports both **Person-to-Person (P2P)** and **Application-to-Person (A2P)** SMS communication over **SMPP**.

---

## Architecture Overview

The system follows an **Intercept and Re-inject** model managed by an external ESME implemented using Java Spring Boot.

The Spring Boot application:

- Acts as an **SMPP Server** for incoming SMS traffic from the MSC.
- Acts as an **SMPP Client** for reinjecting approved messages into the MSC.
- Accepts connections from external A2P applications.
- Sends SMS content to an LLM-based spam detection service.
- Blocks messages classified as spam.
- Re-injects legitimate messages into the GSM network.

# Message Flows

## 1. P2P — Person-to-Person

This flow handles SMS communication between two mobile subscribers registered on the virtual GSM network.

### Flow

1. **Origin**  
   Mobile Station 1 (MS 1) sends an SMS to Mobile Station 2 (MS 2).

2. **Interception**  
   The MSC receives the SMS and forwards the message through SMPP using a `deliver_sm` packet to the Spring Boot SMPP server.

3. **AI Evaluation**  
   The Java Spring Boot application extracts the SMS payload and sends it to the integrated LLM spam classifier.

4. **Decision**
   - `SPAM` → Message is blocked.
   - `HAM` → Message is allowed to continue.

5. **Re-injection**  
   For legitimate messages, the Spring Boot SMPP client constructs a `submit_sm` packet and sends it back to the MSC.

6. **Delivery**  
   The MSC locates MS 2 and delivers the SMS through the virtual GSM radio network.

```text
MS 1
 │
 │ SMS
 ▼
MSC
 │
 │ deliver_sm
 ▼
Spring Boot SMPP Server
 │
 │ SMS Text
 ▼
LLM Spam Classifier
 │
 ├──── SPAM ────► BLOCK
 │
 └──── HAM ─────► SMPP Client
                       │
                       │ submit_sm
                       ▼
                      MSC
                       │
                       │ GSM SMS
                       ▼
                      MS 2
```

---

## 2. A2P — Application-to-Person

This flow handles SMS messages generated by external applications, such as banking systems, notification platforms, and marketing services.

### Flow

1. **Origin**  
   An external application connects to the Spring Boot service as an SMPP client.

2. **Submission**  
   The external application submits an SMS message.

3. **AI Evaluation**  
   The Spring Boot application extracts the SMS content and evaluates it using the LLM spam classifier.

4. **Decision**
   - `SPAM` → Message is rejected.
   - `HAM` → Message is allowed.

5. **Injection**  
   The Spring Boot SMPP client sends the approved SMS to the MSC using `submit_sm`.

6. **Delivery**  
   The MSC resolves the destination subscriber and delivers the message to the mobile station.

```text
External Application
        │
        │ submit_sm
        ▼
Spring Boot ESME
        │
        │ SMS Text
        ▼
LLM Spam Classifier
        │
   ┌────┴────┐
   │         │
 SPAM       HAM
   │         │
 BLOCK    submit_sm
             │
             ▼
            MSC
             │
             ▼
            MS
```

### Configuration

The `config/` directory contains the primary configuration files for the virtual GSM network.

- `osmo-bsc.cfg` — BSC configuration
- `osmo-bts.cfg` — BTS configuration
- `osmo-hlr.cfg` — HLR configuration
- `osmo-msc.cfg` — MSC configuration, including SMPP on port `2775`
- `osmo-stp.cfg` — STP and signaling configuration

### Mobile Configurations

The virtual mobile stations are configured through:

```text
mobile.cfg
mobile2.cfg
```

These files define the parameters and logging configuration for the virtual handsets.

### Persistent Data

The `data/` directory contains persistent network data:

```text
data/
├── hlr.sqlite3
├── mobile/
└── mobile-2/
```

The HLR database stores subscriber information, while the mobile directories contain the corresponding virtual handset data.

# Deployment

## Prerequisites

The project requires:

- Docker
- Docker Compose
- Java / Spring Boot
- An LLM-compatible spam classification service
- SMPP client/server support

---

## 1. Start the GSM Core Network

From the project root:

```bash
docker compose up -d
```

Verify that the containers are running:

```bash
docker compose ps
```

The virtual GSM network should bring up the required components, including:

```text
OsmoBTS
OsmoBSC
OsmoMSC
OsmoHLR
OsmoSTP
OsmoMobile
```

---

## 2. Start the AI SMS Filter

Start the Java Spring Boot SMPP middlebox application.

The application should:

1. Connect to the MSC's SMPP interface.
2. Bind its SMPP server for incoming SMS traffic.
3. Accept external A2P SMPP connections.
4. Send SMS payloads to the LLM classifier.
5. Block messages classified as spam.
6. Re-inject legitimate messages into the MSC.

The MSC SMPP interface is configured on port:

```text
2775
```

# Spam Detection

The AI filter classifies SMS messages into two categories:

### HAM

Legitimate or normal messages.

Example:

```text
Hello, this is a clean test message.
```

The message is allowed and re-injected into the GSM network.

### SPAM

Messages identified as spam, phishing, fraud, or unsolicited marketing.

Example:

```text
Congratulations! You have won 50,000 EGP.
Send us your OTP to claim your prize.
```

The message is blocked and is **not re-injected** into the GSM network.

# Core Design Concept

The main idea of the project is to place an intelligent inspection layer between the SMS routing infrastructure and the final subscriber.

```text
                ┌──────────────────────┐
                │    Mobile Network    │
                │                      │
                │  MS → MSC → SMS      │
                └──────────┬───────────┘
                           │
                           ▼
                ┌──────────────────────┐
                │  SMPP AI Middlebox   │
                │                      │
                │  Intercept           │
                │       ↓              │
                │  Analyze             │
                │       ↓              │
                │  Classify            │
                │       ↓              │
                │  Filter              │
                │       ↓              │
                │  Re-inject           │
                └──────────┬───────────┘
                           │
                           ▼
                ┌──────────────────────┐
                │    Mobile Network    │
                │                      │
                │  MSC → MS            │
                └──────────────────────┘
```

This approach demonstrates how **AI-based security and content inspection can be integrated directly into telecommunications signaling and messaging workflows**.
